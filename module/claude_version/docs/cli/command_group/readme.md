# Command Groups

### Scope

- **Purpose**: Formalize sets of commands that share one implementing function and one parameter set, differing only in default values.
- **Responsibility**: Define command_group membership under a strict identity test — same routine function, same parameter set — distinct from the looser cross-command relationships already noted in `command/*.md` "Related Commands" tables (e.g. `.config` as the "unified predecessor" of `.settings.*`, `.version.paths` as a superset of `.runtime_files`).
- **In Scope**: Group membership, the Representation Absorption Test applied per candidate pair, shared-handler citations, default divergence (when any exists), and cross-references to commands/parameters/tests/user stories.
- **Out of Scope**: Individual parameter semantics (-> `../param/`), namespace-level command reference (-> `../command/`), cross-parameter constraints (-> `../004_parameter_interactions.md`).

Every command registered in `register_commands()` (`src/lib.rs:69-108`) is evaluated against every other command using the Representation Absorption Test (see Evaluated, Not Qualifying below) before a new command name is ever added — this is a mandatory design gate, not documentation-after-the-fact. A proposed new command that would pass the test is a pre-configured alias of an existing command's routine, not a new command_group member requiring its own dispatch function. Every command belongs to exactly one group — including a command with no sibling, which still opens its own Singleton Group and still receives a row below; no command is ever left out of **All Groups**. Before adding a new command, this same evaluation also asks whether an existing group's handler could absorb it via a new parameter instead of a new dispatch function. (Per this workspace-group's shared rulebook, CLI Documentation: Command Group Total Partition and Command Group Minimization.)

**Total:** 15 groups for 15 commands (15 singletons) — a 1:1 ratio; no multi-member group qualifies yet. All 15 documented `clv` commands were evaluated pairwise under the Representation Absorption Test, backed by a full pairwise dispatch-function grep sweep (not informal reasoning) — every one of the 14 dispatch functions listed below was checked as a grep target against the entire `src/` tree, excluding its own `fn name(...)` definition line. `register_commands()` (`src/lib.rs:94-107`) registers each command with its own uniquely-named routine — `status_routine` (`src/commands/status.rs:236`), `version_show_routine` (`src/commands/version.rs:26`), `version_install_routine` (`src/commands/version.rs:75`), `version_guard_routine` (`src/commands/version.rs:240`), `version_list_routine` (`src/commands/version.rs:655`), `ps_routine` (`src/commands/process.rs:20`), `ps_kill_routine` (`src/commands/process.rs:155`), `settings_show_routine` (`src/commands/settings.rs:16`), `settings_get_routine` (`src/commands/settings.rs:72`), `settings_set_routine` (`src/commands/settings.rs:119`), `config_routine` (`src/commands/config.rs:39`), `params_routine` (`src/commands/params.rs:34`), `runtime_files_routine` (`src/commands/runtime_files.rs:29`), `paths_routine` (`src/commands/paths.rs:97`) — 14 distinct functions for 14 dispatched commands, each its own Singleton Group. `version_list_routine`'s `mode::history` branch further delegates to `render_history_mode()` (`src/commands/history.rs:239`, the absorbed former `version_history_routine`) — a within-group implementation detail, not a 15th dispatched command. `.help` is intercepted in `src/adapter.rs::argv_to_unilang_tokens()` (`src/adapter.rs:130`) before the unilang pipeline runs at all and never reaches a routine — it is documented as Command #1 in `command/root.md` and therefore still receives its own Singleton Group above (Group 1), with the interception function cited as its Shared Handler in place of a dispatch routine.

The sweep result: zero cross-calls found for any of the 14 functions — running `grep -rn "$fn(" src/ | grep -v "fn $fn"` for every one of the 14 names above returns an empty result set in every case (each routine name appears only at its own `pub fn` definition and as a bare, uncalled identifier passed to `Box::new(...)` in `register_commands()`, which the `fn $fn` exclusion also filters since that identifier form has no trailing `(`). No routine in `src/commands/*.rs` calls another routine directly. This is architecturally different from claude_runner's `dispatch_ask() -> dispatch_run()` delegation, which is exactly the shape this entity looks for and did not find here.

Beyond the routine-to-routine sweep, every private helper reachable from more than one routine was checked for how many distinct routines actually call it — a helper shared narrowly (2 routines) is a real near-miss requiring parameter-set comparison; a helper shared broadly (3+ routines, no coherent subset) is generic infrastructure, not a "shared handler" in the entity's sense:

| Helper | Defined | Distinct calling routines | Breadth |
|---|---|---|---|
| `is_dry()` | `src/commands/mod.rs:66` | `config_routine`, `settings_set_routine`, `version_install_routine`, `version_guard_routine`, `ps_kill_routine` (5) | Generic |
| `is_force()` | `src/commands/mod.rs:73` | `version_install_routine`, `version_guard_routine`, `ps_kill_routine` (3) | Generic |

| `require_nonempty_string_arg()` | `src/commands/mod.rs:50` | `settings_get_routine`, `settings_set_routine` (2) | Narrow — see Evaluated, Not Qualifying |

`is_dry`, `is_force`, and `require_claude_paths` remain generic, many-caller utilities with no coherent 2-command subset driving the sharing — confirmed by the caller counts above, not merely asserted. `require_nonempty_string_arg` and `config_resolve_context`, by contrast, are each called from exactly 2 routines and were evaluated individually as near-miss candidates (see Evaluated, Not Qualifying below) precisely because a 2-caller helper is the shape a real command_group candidate would produce if the two callers also shared a parameter set — neither pair does.
