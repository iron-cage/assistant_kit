# Command Groups

### Scope

- **Purpose**: Formalize sets of commands that share one implementing function and one parameter set, differing only in default values.
- **Responsibility**: Define command_group membership under a strict identity test — same routine function, same parameter set — distinct from the looser per-parameter cross-command groupings in `param_group/`.
- **In Scope**: Group membership, the Representation Absorption Test applied per candidate pair, shared-routine citations, default divergence (when any exists), and cross-references to commands/parameters/tests/user stories.
- **Out of Scope**: Individual parameter semantics (-> `../param/`), per-parameter cross-command groupings that don't require an identical full parameter set or a shared routine (-> `../param_group/`).

Every command belongs to exactly one group — including a command with no sibling, which still opens its own Singleton Group and still receives a row below; no command is ever left out of **All Groups**. This is Command Group Total Partition, canonical at `cli_doc_des.rulebook.md § Commands Documentation : Representation Absorption Test · OC166`. Before adding a new command, this same evaluation also asks whether an existing group's handler could absorb it via a new parameter instead of a new dispatch function — Command Group Minimization, canonical at `cli_doc_des.rulebook.md § Commands Documentation : Command Group Minimization · OC167`.

Every command in `command/` is evaluated against every other command using the Representation Absorption Test before a new command name is ever added — this is a mandatory design gate, not documentation-after-the-fact. A proposed new command that passes the test is a pre-configured alias of an existing command's routine, not a new command_group member requiring its own dispatch registration.

**Representation Absorption Test** (full definition, verification method, and rationale: `cli_doc_des.rulebook.md § Commands Documentation : Representation Absorption Test · OC166`): a candidate pair qualifies as a `command_group` only when BOTH hold — (1) **identical routine function**, and (2) **identical CLI-facing parameter set**, differing at most in default values. A shared private helper function (e.g. `resolve_cmd_path`, `create_storage`) does NOT satisfy criterion 1 — that is ordinary code reuse, not command identity. See Evaluated, Not Qualifying below.

### Command Removal: `.list` -> `.projects`

`.list` and `.projects` were evaluated as part of the pairwise Representation Absorption Test sweep (see the `.status`/`.list` row above for `.list`'s own verified parameter set) and never qualified for an automatic command_group merge: distinct routine functions (`list_routine()` at `src/cli/list.rs:44` vs `projects_routine()` at `src/cli/projects.rs:449`, neither calling the other — confirmed by the same cross-call sweep methodology used throughout this file) and non-identical parameter sets (`.list`'s naming-scheme/session-family view vs `.projects`' scope-bounded session-grouped view). The Representation Absorption Test's question — "would the proposed command be achievable by changing default values of an existing command's parameters?" — correctly answered no for this pair; the two commands did different things by design, not by accident.
