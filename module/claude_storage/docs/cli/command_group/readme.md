# Command Groups

### Scope

- **Purpose**: Formalize sets of commands that share one implementing function and one parameter set, differing only in default values.
- **Responsibility**: Define command_group membership under a strict identity test — same routine function, same parameter set — distinct from the looser per-parameter cross-command groupings in `param_group/`.
- **In Scope**: Group membership, the Representation Absorption Test applied per candidate pair, shared-routine citations, default divergence (when any exists), and cross-references to commands/parameters/tests/user stories.
- **Out of Scope**: Individual parameter semantics (-> `../param/`), per-parameter cross-command groupings that don't require an identical full parameter set or a shared routine (-> `../param_group/`).

Every command belongs to exactly one group — including a command with no sibling, which still opens its own Singleton Group and still receives a row below; no command is ever left out of **All Groups**. Before adding a new command, this same evaluation also asks whether an existing group's handler could absorb it via a new parameter instead of a new dispatch function. (Per this workspace-group's shared rulebook, CLI Documentation: Command Group Total Partition and Command Group Minimization.)

Every command in `command/` is evaluated against every other command using the Representation Absorption Test before a new command name is ever added — this is a mandatory design gate, not documentation-after-the-fact. A proposed new command that passes the test is a pre-configured alias of an existing command's routine, not a new command_group member requiring its own dispatch registration.

**Representation Absorption Test:** "Would the proposed new command be achievable by changing default values of an existing command's parameters?" A candidate pair qualifies as a `command_group` only when BOTH hold:

1. **Identical routine function** — both commands are registered in `src/cli_main.rs`'s `routines` phf map against the literal same function, or one's routine is a thin, unconditional delegate that calls the other's routine directly (not a shared lower-level helper).
2. **Identical CLI-facing parameter set** — every parameter accepted by one is accepted by the other, differing at most in default values.

A shared private helper function (e.g. `resolve_cmd_path`, `create_storage`) does NOT satisfy criterion 1 — that is ordinary code reuse, not command identity. See Evaluated, Not Qualifying below.

### Command Removal: `.list` -> `.projects`

`.list` and `.projects` were evaluated as part of the pairwise Representation Absorption Test sweep (see the `.status`/`.list` row above for `.list`'s own verified parameter set) and never qualified for an automatic command_group merge: distinct routine functions (`list_routine()` at `src/cli/list.rs:43` vs `projects_routine()` at `src/cli/projects.rs:696`, neither calling the other — confirmed by the same cross-call sweep methodology used throughout this file) and non-identical parameter sets (`.list`'s naming-scheme/session-family view vs `.projects`' scope-bounded session-grouped view). The Representation Absorption Test's question — "would the proposed command be achievable by changing default values of an existing command's parameters?" — correctly answered no for this pair; the two commands did different things by design, not by accident. There is no missing "Evaluated, Not Qualifying" row for this pair to add retroactively — this section supersedes the need for one, since the pair's relationship changed from "evaluated, not qualifying" to "deliberately consolidated" by explicit decision rather than by a later RAT re-evaluation finding a different answer.

This section documents a different, deliberate action: **consolidation by capability absorption**, not a RAT-qualifying merge. `.list`'s distinguishing capabilities — project-only terse view, path-substring filtering, naming-scheme filtering, and raw conversation-ID scripting output — are being added to `.projects` as new parameters (`detail::`, `filter::`, `type::`, `ids::`; see [`07_projects.md`](../command/07_projects.md)) rather than kept as a second command with its own routine and dispatch registration. This is a product/UX decision — one command surface for all project/session listing needs, with `scope::` meaning the same thing everywhere it appears — not a mechanical dedup finding. `.list` is deprecated (see [`02_list.md`](../command/02_list.md)); its row in **All Groups** above is retained per the Command Group Total Partition rule until the routine itself is removed from `src/cli_main.rs`'s `routines` phf map — a source-code change tracked as implementation work, not a documentation change.

**Why this doesn't retroactively fail Command Group Minimization:** the mandatory pre-addition Representation Absorption Test gate exists to catch *accidental* duplication when a *new* command is proposed — it does not mandate that every pair of commands which once failed it must stay separate forever. A deliberate later decision to collapse two already-differentiated commands into one is evaluated on its own product/UX merits (one listing surface, consistent `scope::` semantics across the whole CLI, no risk of a user confusing which command's `path::` means what), not on whether the RAT would have caught it automatically. Once the removal is implemented, **All Groups** drops to 13 groups for 13 commands and this section's "planned" language is updated to past tense per `doc_des.rulebook.md § Collection : Doc Instance Deprecation Procedure (OD069)`.
